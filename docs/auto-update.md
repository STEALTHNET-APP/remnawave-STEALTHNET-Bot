# Обновления панели и бота

Начиная с 6.7.1 в настройках есть раздел «Обновления». Он показывает версию запущенного API, коммит, дату сборки, состояние установки и последние изменения. Коммит меняется при каждой сборке через установщик, Makefile или службу обновления; повторная сборка одного коммита не считается новой версией. `version.json` задаёт номер выпуска. Для следующего выпуска измените его и выполните `node scripts/sync-version.cjs`.

Проверка выполняется при запуске службы и каждые 15 минут, даже если автоматическая установка выключена. В админке на всех страницах появляется предложение обновиться. Для установки можно нажать кнопку или включить ежедневную установку в выбранный час UTC.

- **Получать последние обновления** — последний коммит `main`. Номер в `version.json` менять для обнаружения обновления не требуется: сравниваются коммиты. Все промежуточные изменения входят в обновление.
- **Получать только новые релизы** — последний опубликованный стабильный GitHub Release и коммит его тега. Изменения `version.json` без публикации Release недостаточно.

Черновики, prerelease, откат на старую историю и расходящиеся ветки не устанавливаются. Проверка GitHub не останавливает панель. Автоматическая установка по умолчанию выключена.

## Первичная установка

Нужны Linux с systemd, Python 3.9+, Git, Docker и Docker Compose с поддержкой `up --wait`. Поддерживается стандартный проект `stealthnet` из этого репозитория, с сервисами `postgres`, `api`, `broadcast-worker`, `bot`, `frontend`, а также `console` и встроенным `nginx`, если они запущены. Исходники должны быть в обычной ветке Git. Для установки по расписанию рабочая копия должна быть чистой. Ручная установка позволяет отдельно сохранить локальные правки перед обновлением; `.env`, штатные игнорируемые настройки и неотслеживаемый `docker-compose.override.yml` остаются на месте. Сгенерированный установщиком `nginx/nginx.conf` сохраняется вместе с доменом и SSL-настройками, даже если он отслеживается Git. Docker rootless и нестандартные имена образов требуют отдельной настройки и этим установщиком не поддерживаются.

Сначала сохраните резервную копию БД штатным инструментом панели, обновите исходники до 6.7.1 и проверьте миграции текущей установки. Затем из папки проекта:

```bash
sudo bash scripts/updater/install.sh
export STEALTHNET_BUILD_COMMIT="$(git rev-parse HEAD)"
export STEALTHNET_BUILD_DATE="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
docker compose build api bot frontend
docker compose stop bot broadcast-worker api
docker compose up --no-deps --no-build --exit-code-from frontend frontend
docker compose up -d --no-deps --no-build --wait api
docker compose up -d --no-deps --no-build --wait bot broadcast-worker
```

Если nginx на хосте читает файлы из `/var/www/stealthnet`, при **первой** установке передайте эту папку:

```bash
sudo bash scripts/updater/install.sh /var/www/stealthnet
bash scripts/update-front-with-external-nginx.sh
```

Для существующей конфигурации служба сохраняет настройки: изменить путь можно в `/etc/stealthnet-updater/config.json` (`externalFrontend`), затем `sudo systemctl restart stealthnet-updater`. Это должна быть отдельная папка только для собранного фронтенда: её содержимое заменяется при обновлении. Для встроенного nginx `externalFrontend` должен быть `null`.

Откройте «Настройки → Обновления», выберите канал, сохраните настройки и нажмите «Проверить обновления». Номер сборки должен совпадать с `git rev-parse HEAD` на сервере. Если панель была собрана прямым `docker compose build` без переменных версии, пересоберите её с переменными выше.

Сам установщик проекта выставляет метаданные сборки, но отдельная служба устанавливается явно командой выше. Одного обновления файлов Git недостаточно — существующие контейнеры нужно пересобрать.

## Что происходит при обновлении

1. Служба получает код только из `STEALTHNET-APP/remnawave-STEALTHNET-Bot`, проверяет историю Git, локальные изменения, коммит запущенного API и место на диске.
2. Собирает API, бот, фронтенд и консоль. Обработчик рассылок использует образ API. Текущая версия пока работает.
3. Восстанавливает снимок БД в отдельный PostgreSQL в изолированной Docker-сети без выхода в интернет. Новая версия применяет миграции и проверяет соответствие таблиц/полей Prisma. Проверочный API не запускает фоновые задачи и отвечает только на healthcheck. Письма, платежи и Telegram при этой проверке не вызываются.
4. Останавливает API, бот, обработчик рассылок и консоль. Создаёт свежую резервную копию БД, исходников, `.env`, Compose, nginx, загрузок, вложений рассылок и данных консоли. Старые Docker-образы закрепляются отдельными тегами.
5. Устанавливает код и фронтенд. API применяет миграции, оставаясь в режиме обслуживания с ответом HTTP 503 на пользовательские запросы. Проверяет API, обновляет встроенный nginx, если он используется.
6. Возобновляет приём запросов и фоновые службы. Код службы обновления также перечитывается после успешного обновления.

При ошибке **до возобновления приёма запросов** восстанавливаются БД, файлы, исходники и старые образы. При ошибке **после возобновления работы** автоматический откат БД запрещён: он мог бы потерять новые платежи или регистрации. Служба сохраняет копию, показывает ошибку и требует проверки на сервере.

Есть перерыв в работе панели и бота на время финальной копии, миграций и запуска. Существующие VPN-подключения Remnawave не меняются. Проверка запуска не заменяет функциональные тесты перед публикацией кода.

Обновления схемы БД, приложения, конфигурации существующих служб, nginx и кода updater поддерживаются. Изменение версии PostgreSQL, состава служб, сетей или подключений хранилищ требует отдельной подготовки сервера. Собственные незакоммиченные правки блокируют установку по расписанию. Для ручной установки с сохранением правок используйте отдельную кнопку ниже. Старые версии без режима проверки миграций сначала нужно обновить вручную до 6.7.1.

## Резервные копии

Перед каждой установкой создаётся каталог `/var/lib/stealthnet-updater/backup-*`, доступный только root. По умолчанию копии хранятся **3 дня**; в панели можно выбрать 1–30 дней. Очистка выполняется ежедневно, включая дни без обновлений. Копия незавершённого или неудачного обновления с требованием восстановления не удаляется автоматически. Старые копии версии 6.7.0 без `manifest.json` также не удаляются автоматически.

Состав: `database.dump`, `source.tar`, `settings.tar.gz`, `files-*.tar.gz`, `files.json`, `images.json`, `manifest.json`. Docker-образы остаются на этом сервере под тегами `stealthnet-backup-*`; теги снимаются после истечения срока копии. Копии обновлений не заменяют резервное копирование на другой сервер. Уже существующий раздел резервных копий БД работает отдельно.

Служба работает на хосте, слушает Unix-сокет с правами `0600`; наружного порта и доступа веб-контейнера к Docker socket нет. Маршруты обновления доступны только полной роли `ADMIN`, даже если менеджеру выдали раздел настроек.

## Локальные изменения и неактивная кнопка

Изменение только сгенерированного `nginx/nginx.conf` не блокирует обновление: служба копирует действующий конфиг в резервную копию и возвращает его после переключения исходников. Новая версия шаблона не подменяет домен и SSL-настройки владельца. При откате также возвращается прежний конфиг. Удалённый, символически связанный или добавленный в индекс конфиг требует проверки.

Если обновление найдено, но обычная кнопка неактивна, посмотрите причину блокировки. При локальных изменениях панель показывает имена файлов. Это могут быть изменения от установочных команд или дополнительные файлы в папке проекта, а не только ручная правка исходников.

Кнопка **«Сохранить правки и обновить»** требует отдельного подтверждения администратора. Сначала выполняются сборка, проверка миграций и резервное копирование. Перед переключением версии правки, включая staged и новые неигнорируемые файлы, сохраняются в Git stash и в `local-changes.bundle` внутри папки резервной копии. Затем устанавливаются исходники обновления. Локальные правки **не применяются** к новой версии автоматически. Если файлы изменились после подтверждения, установка останавливается.

`.env` должен быть штатно исключён из Git. Неотслеживаемый `docker-compose.override.yml` остаётся на месте и продолжает участвовать в сборке и запуске. Конфликты Git, изменения отслеживаемых `.env` / `docker-compose.override.yml`, вложенные репозитории и detached HEAD требуют отдельной проверки на сервере. Подтверждение не отменяет проверок совместимости хранилищ, служб и истории Git.

При откате до возобновления приёма запросов возвращаются прежняя версия и её локальные правки, включая индекс Git. Если восстановление правок не удалось, службы остаются остановленными, включается `recoveryRequired`. Копии с локальными правками **не удаляются по расписанию**: их удаляет администратор после проверки. Git stash также сохраняется.

Для извлечения правок из независимой копии в отдельный репозиторий, не затрагивая работающую панель:

```bash
mkdir recovered-local-changes
cd recovered-local-changes
git init
git fetch /var/lib/stealthnet-updater/backup-ИМЯ/local-changes.bundle refs/stash:refs/recovery/local-changes
git checkout -b recovery 'refs/recovery/local-changes^1'
git stash apply --index refs/recovery/local-changes
```

Укажите реальный путь из панели. Копия может содержать приватные настройки — не публикуйте её.

В уже установленной старой версии этой кнопки нет: исправление интерфейса, API и службы необходимо сначала доставить на сервер. Если блокировку вызывает только `nginx/nginx.conf`, используйте одноразовый запуск новой службы из отдельной временной папки:

```bash
cd /opt/remnawave-STEALTHNET-Bot
git fetch https://github.com/STEALTHNET-APP/remnawave-STEALTHNET-Bot.git main
update_repair_dir="$(mktemp -d /var/tmp/stealthnet-update-repair.XXXXXX)"
git archive FETCH_HEAD scripts/updater | tar -x -C "$update_repair_dir"
sudo python3 "$update_repair_dir/scripts/updater/recover-update.py" --channel main
```

Это обновляет до актуального `main`, не меняет выбранный канал и расписание для следующих обновлений. Исходники работающей панели до этапа установки не заменяются. Скрипт проверяет блокировку операции, временно останавливает службу обновления и запускает её после завершения. Сохраняются обычные проверки, резервная копия и откат. Другие локальные правки автоматически не убираются. При ошибке сначала изучите журнал, а не повторяйте установку вслепую.

Для диагностики достаточно `git status --short` из папки проекта. Не выполняйте `git reset --hard` или `git clean` для разблокировки без сохранения и проверки файлов. После обновления файлов службы требуется `sudo systemctl restart stealthnet-updater` вне активной установки.

## Ошибки и восстановление

```bash
sudo systemctl status stealthnet-updater
sudo journalctl -u stealthnet-updater -n 100
sudo tail -100 /var/lib/stealthnet-updater/update.log
docker compose ps
```

Логи и резервные копии доступны только root и могут содержать служебные сведения. Не публикуйте их целиком. Контролируйте свободное место. Копии неудачных обновлений сохраняются сверх выбранного срока, пока требуется восстановление.

Если сервер или служба остановились посреди обновления, автоматический повтор заблокирован. В `/var/lib/stealthnet-updater/status.json` будут `recoveryRequired: true` и путь `backup`. Проверьте коммит, образы и БД. В папке резервной копии `images.json` хранит прежние образы; `settings.tar.gz` — настройки; `database.dump` — БД. Не восстанавливайте БД поверх новых пользовательских записей без отдельного решения.

После ручного восстановления остановите службу, сохраните `status.json` для диагностики и измените в нём `recoveryRequired` на `false`, `phase` на `idle`, затем запустите службу. Настройки расписания лежат отдельно в `settings.json`.

Чтобы отключить автоматическую установку, снимите переключатель в панели. Чтобы остановить всю службу, используйте `sudo systemctl disable --now stealthnet-updater` вне активного обновления.
