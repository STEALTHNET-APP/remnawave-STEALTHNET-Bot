# Проверка подписок при /start

Исправление по сообщению Владимира в STEALTHNET SOFTWARE → Flood от 13 ноября: покупка через бота могла создавать отдельную подписку вместо продления уже имеющейся.

## Поведение

- Вход через бота проверяет все VPN-профили с подтверждённым Telegram ID, даже если основная подписка уже привязана. Используется `/api/users/stream` с курсорной пагинацией; для старой версии Remna предусмотрен `/api/users/by-telegram-id`. Ответ с чужим или отсутствующим Telegram ID, неполная пагинация и ошибка API не считаются отсутствием подписки.
- Восстановление сохраняет существующие ID, тарифы и основную подписку. Записи другого владельца не переносятся: пользователю предлагается войти на сайт и привязать Telegram в профиле.
- При покупке сначала предлагается продление существующей подписки. Новая отдельная подписка требует явного выбора и доступна при включённой мультиподписке. Импортированный VPN-профиль без тарифа можно продлить, выбрав тариф с сохранением ID и ссылки.
- VPN-покупка повторно проверяет подписки, включая старые кнопки оплаты. При сбое проверки вход в бот сохраняется с признаком незавершённой проверки; независимые покупки, баланс и остальные разделы не блокируются этой проверкой.
- Бот напоминает о привязке аккаунта сайта, если доступных для продления подписок нет. Автоматического объединения аккаунтов по имени или email нет.

## Проверки

- Сборки backend и bot: успешно.
- 72 модульных теста бота: успешно (`node --import tsx --test src/*.test.ts`).
- 22 сценария обработчиков продления/покупки: успешно. В том числе сохранение `extendsSecondarySubId` до оплаты, явная отдельная покупка, импортированный профиль без тарифа, несколько подписок, недоступность проверки и старые кнопки оплаты.
- 14 проверок API и восстановления: успешно. Пагинация, старый API, повторные ID, повторный `/start`, сохранение основной подписки, конфликт владельца, сбой Remna и авторизация бота. Использовались изолированные заглушки БД и провайдера, без списаний.
- На стенде актуальный поиск Remna возвращает профиль тестового пользователя; старый endpoint возвращает 404.
- В Telegram Web проверены два вызова `/start`, экран «Тарифы» и переход к продлению существующего триала. После проверки у тестового пользователя осталась одна подписка; новых платежей за время проверки нет.
- API, бот и worker после выкладки работают без перезапусков; API прошёл healthcheck.

## Стенд и откат

Код исправления: `09f02be`. Образы: `stealthnet-api:start-discovery-nov13`, `stealthnet-bot:start-discovery-nov13`. Фронтенд не менялся.

Резервная копия на сервере: `/opt/stealthnet-backups/pre-start-discovery-20261113`. Содержит дамп PostgreSQL, исходники backend/bot и Compose. Сохранены образы `stealthnet-api:pre-start-discovery-nov13` и `stealthnet-bot:pre-start-discovery-nov13`.

Для отката к предыдущему запуску восстановить `docker-compose.override.yml` из этой копии и пересоздать только `api`, `broadcast-worker`, `bot` с `--no-build --no-deps`. Миграций в исправлении нет; восстанавливать дамп БД для обычного отката кода не требуется.

Уже существующие дубли не удалялись и не объединялись. Реальные списания и все мобильные клиенты Telegram не проверялись. Опубликованный тег `v7.0.0` не изменялся; исправление находится в последующих коммитах main.

Контракт актуального поиска: https://github.com/remnawave/backend/blob/main/libs/contract/commands/users/get-users-stream.command.ts
